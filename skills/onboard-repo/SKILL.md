# onboard-repo

Goal: one short, accurate snapshot of how *this* repo works, so new code and reviews match it instead of an ideal architecture. Keep the cost low: survey with the `Explore` agent and don't read whole files in this session.

## Steps

1. **Check what exists.** If `.claude/project-profile.md` already exists and the user didn't ask to refresh it, say it's already onboarded (one line, with the date in its header) and stop. On a refresh, keep every section marked `(human)` exactly as it is.

2. **Survey** with one `Explore` call that asks all of these at once, answered as `path:line` notes:
   - Languages and versions, frameworks, package manager and manifests, build tool.
   - Entry points (main/server/CLI/handlers/jobs) and the top-level layout. Which directory owns which responsibility (API, domain, data access, LLM/agents, config, tests)?
   - Conventions, each with one example location: error handling, logging, config loading, DB access, HTTP clients, dependency injection, async model, naming.
   - Tests: framework, location, and the command to run them. Lint/format/type tools. CI config.
   - Business intent sources: README, docs/, ADRs, PRDs, CONTRIBUTING, CHANGELOG, any `*BUSINESS*` or `*PRODUCT*` docs, ticket-ID patterns in branch names or commits (`git log --oneline -40`).
   - Debt signals: the 10 largest source files (`git ls-files | xargs wc -l 2>/dev/null | sort -n | tail -12`), god files, deprecated libraries, and TODO/FIXME clusters.

3. **Write `.claude/project-profile.md`** (under ~120 lines) with these sections:
   - Header: `Generated by onboard-repo on <date>. Edit freely; mark sections you own with (human) and refresh will keep them.`
   - **Stack**
   - **Layout and responsibilities**: `path/` → what lives there
   - **Conventions to follow in new code**: each with an example `path:line`
   - **Known debt**: don't copy into new code, don't fix unasked; include god files with line counts
   - **How to run, test, lint**
   - **Business context sources**: paths, ordered by usefulness, one line each on what they cover
   - **Open questions**: things the code can't tell you, e.g. who the users are and which rules are policy versus accident

   Only state what the survey found. Mark guesses as `(inferred)`.

4. **Write `.claude/tarjog.toml`** only if the business sources found differ from the global defaults ({{business_context}}). If the file already exists, merge into it and keep its other sections:
   ```toml
   [review]
   business_context = ["<best source>", "<next>"]
   ```

5. **No business context at all?** Don't invent one. Add it to Open questions, then offer to draft `docs/BUSINESS_CONTEXT.md` from `{{repo_dir}}/templates/BUSINESS_CONTEXT.md` by asking the user at most 5 short questions.

6. **Keep it local by default.** Run `{{repo_dir}}/bin/tarjog project <repo path>`. It adds tarjog's files to `.git/info/exclude`, which ignores them for you only and leaves the team's `.gitignore` alone. It skips any file the team already tracks. Don't edit `.git/info/exclude` by hand. Tell the user they can commit the files if the team wants them.

7. **Report** in at most 8 lines: the stack, the 3 most important conventions, the top debt item, the business sources found (or missing), and the paths written.
